# エビデンスデータベースの作り方(Step 2 詳細)

知識ゼロの分野でも書ける理由は、知識を自分の頭に持つのではなく、検証済みの論文をファイルに集めておくから。この工程の質が、記事全体の信頼性の上限を決める。

## 検索の進め方

1. ユーザーからテーマ(例:夜泣き)の日本語キーワードをもらう、または一緒に決める。
2. 日本語キーワードを検索用の英語キーワードに変換する(例:「夜泣き 睡眠 乳児」→ "infant night waking sleep")。
3. 学術検索(WebSearch/WebFetchで PubMed, Google Scholar, semantic scholar 等にアクセスできる場合はそれを使う。専用APIツールが利用可能ならそちらを優先する)で候補論文を探す。
4. 見つけた論文は、まず「本当に存在するか」を疑ってから次に進む。タイトルや著者名が本物らしく見えても、AIが生成した架空の論文である可能性は常にある。

## DOI検証(最重要・省略不可)

- DOIが存在し、実際に解決する(doi.orgや出版社サイト、CrossRefなどで実在確認できる)論文だけをデータベースに入れる。
- DOIが見つからない論文、検証できない論文は**入れない**。「たぶん実在する」で妥協しない。
- 自分の記憶やそれらしい知識から論文情報を書き出すことは絶対にしない。実際に取得できたソースからのみ記録する。
- 迷ったら入れない側に倒す。データベースが小さくなっても、嘘が混じるより良い。

## 1件のエントリに書く3つだけの情報

多く書きすぎない。以下の3項目に絞ることで、後で「何が本当に分かっていて、何がまだ弱いのか」を一目で判断できるようにする。

1. **書誌情報**:タイトル・発表年・掲載誌・DOI
2. **分かったこと**:1〜3行で、その論文が実際に示した結果
3. **研究の限界**:対象人数/対象者の属性、追試の有無などがわかれば書く

「研究の限界」を必ず書く理由:これがあることで、記事本文で「〜という報告があります」(単発の知見)と「〜が分かっています」(再現性があり確立した知見)を書き分けられる。この書き分けができているかどうかが、読者から見た信頼性を大きく左右する。書き分けを誤ると、限定的な知見をあたかも定説であるかのように断定してしまう(オーバークレーム)ことになり、Step 5 の査読で指摘される対象になる。

`assets/evidence-database-template.md` をプロジェクトの `evidence-db.md` としてコピーし、この形式でエントリを追加していく。

## このセッションでできないこと・注意点

- PubMed等の専用APIツールがこのセッションに接続されていない場合、WebSearch/WebFetchでの一般検索が代替手段になる。取得した内容の信頼性(特にDOIの実在)は通常以上に慎重に確認すること。
- 有料のフルテキストにアクセスできない論文は、要旨(アブストラクト)ベースで「分かったこと」を書いて構わないが、要旨から読み取れる範囲を超えて憶測で内容を補わない。

### pubmed.ncbi.nlm.nih.gov / doi.org / api.crossref.org / eutils.ncbi.nlm.nih.gov がWebFetchでブロックされる場合

環境のネットワークポリシー(egress proxy)によっては、これらの学術系ドメインへの直接アクセスが `EGRESS_BLOCKED` として拒否されることがある。これは組織のポリシーによる制限であり、回避を試みたり繰り返しリトライしたりしない。代わりに次の手順で代替検証する:

1. WebSearchで論文タイトル(完全一致に近い形で引用符付き)+ "doi.org" などのキーワードを検索する。WebSearchは直接そのドメインを取得するわけではなく検索インデックス経由のため、多くの場合ブロックされない。
2. 検索結果に、PubMed掲載ページ・出版社サイト(ScienceDirect, Wiley等)・J-STAGE・ResearchGateなど**複数の独立したソース**が現れ、それらが同一のタイトル・著者・DOI・掲載誌を示していることを確認する。1つのソースだけでは不十分。
3. この方法で確認した場合は、データベースのファイル冒頭に「WebSearch経由の複数ソース照合で検証した」旨を明記し、ユーザーに対しても「本番公開前に人間が実際にDOIリンクをクリックして確認することを推奨する」と伝える。この方法は直接DOIを解決する方法の完全な代替にはならないため、弱いことを隠さない。
