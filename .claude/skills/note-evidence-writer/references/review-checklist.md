# 査読(Step 5)のやり方

書いたAI自身に「これで合ってる?」と聞くのは、自分の答案を自分で採点するようなもので、ほぼ意味がない。査読は必ず別のセッション・別のモデル(可能なら別のAI)で行う。

## 査読で見るのは3つだけ

1. **出てくる研究は実在するか**(DOIで再確認する)
2. **数字・固有名詞は論文の通りか**(サンプルサイズ、年齢、割合、手法名、著者名など、具体的で間違えやすい箇所)
3. **論文の結論より強く言い切っていないか**(オーバークレームのチェック。`evidence-db.md` の「研究の限界」欄と照らし合わせる)

③のオーバークレームには、実際のプロジェクトで頻出した2つの具体パターンがある。査読では特にこの2点を重点的に確認する。
- **群内変化と群間差の取り違え**:「介入前後で改善した」を「対照群より改善した/効果があった」と書いていないか。RCTなら、対照群との比較そのものが有意だったかを確認する。
- **特定の一つの介入の結果を、そのクラス全般に一般化していないか**:「あるアプリで効果が見られた」を「アプリ(全般)は効果がある」のように広げていないか。

この3つ以外を広げすぎない。文章表現の好み等はこの査読の対象ではない。

## このセッション(書いたAI自身)でもできること

査読の一部は、別セッションを待たずにその場でできる。省略しない:

- 草稿に登場する全てのDOIを、もう一度実際に解決できるか確認する(データベース作成時から時間が経っていたり、手動編集で誤りが入っていることがある)。
- 草稿中の数字・固有名詞を `evidence-db.md` の該当エントリと1つずつ突き合わせる。
- 各主張の強さが、対応エントリの「研究の限界」欄と矛盾していないか確認する(単発の知見を確立事実のように書いていないか)。

## 別のAI・人間が必要なこと

- 本来の実践では、書いたAI(Claude Code)とは別のAI(例:Google Scholarにアクセスできる Gemini、さらに慎重を期す場合は3つ目のAI)に草稿を渡し、上記3つの観点で独立にチェックしてもらう。「同じAIの新しいスレッド」は文脈の引き継ぎを断つ程度の効果しかなく、同じモデルの同じクセ・同じ間違え方は引き継がれてしまうため、可能な限り別のAIサービスを使うほうが独立性が高い。
- 渡し方は単純で、`evidence-db.md` と原稿(または `full-draft.md`)を別のAIサービスの新しいチャットにアップロード(またはテキストをそのまま貼り付け)し、`assets/second-ai-review-prompt.md` のプロンプトをコピーして一緒に送るだけでよい。返ってきた指摘は、下記の記録フォーマットに転記する。
- このセッションに別AIへの受け渡し手段がない場合は、その旨をユーザーに明確に伝える。「これは安全網の抜け穴であり、可能なら人間が別ツールで確認するか、少なくとも文脈をリセットした上でのセカンドパスを行うべき」と提案する。ただし、これは真に独立した査読の代替にはならないことも伝える。
- DOIで実在確認できない論文は、最終稿から削除する。
- 数字・固有名詞は、AIによる確認に加えて、可能であれば人間の目でも直接確認する。

## 記録フォーマット(`review-notes.md`)

各チェック対象の主張ごとに、以下の形式で記録する。

```
## [章番号] 主張の要約
- 引用元: [論文タイトル / DOI]
- ①実在確認: 済 / 未確認 / NG(理由)
- ②数字・固有名詞: 一致 / 不一致(詳細)
- ③言い切りの強さ: 適切 / オーバークレーム(修正案)
- 対応: 修正済み / 削除 / 要確認のまま(理由)
```

いずれかの項目が「NG」「不一致」「オーバークレーム」のまま「要確認のまま」で残っている記事は、公開しない。
